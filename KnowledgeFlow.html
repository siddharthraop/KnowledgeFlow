Abstract

Product teams write Google's data center documentation. Each team keeps its own documentation set, and each set links well inside itself. Questions from employees often cross sets. In the 2024 Stack Overflow survey, 61% of professional developers spent more than 30 minutes a day searching for answers, and 30% said knowledge silos affected their productivity ten or more times a week2.

KnowledgeFlow is an agent that answers an employee's question with a cited path across documentation sets. It builds a knowledge graph from the structure that writers already maintain: DITA maps, relationship tables, keys, content references, cross-references and subject classifications. Gemini reads prose only to find mentions that have no link. Each edge it finds stays proposed until an information architect approves it.

Fixed checks decide whether an answer is grounded. Every step must cite a topic and the edge that reached it, and every value must match its source. When a step fails, KnowledgeFlow drops that step, says so, and opens a gap issue for writers. An approved edge becomes a relationship table row in the source, so the next build reads it without the model.

§1 Client Brief

Google publishes documentation for its data center products and services. Two of those products are Cloud TPU (Tensor Processing Unit) accelerators and Cloud NAT (network address translation). Different teams write the two documentation sets, and each product publishes release notes.

This MVP uses three samples from the first two projects in this series. The Cloud TPU sample is the DITA set from MANIFEST, with its maps, keys and relationship tables3. The Cloud NAT sample is the MyST Markdown set from the Autonomous Author4. The third sample is the Cloud NAT release notes10. One set is still in DITA and one is already docs as code. That is the state of a team during a migration, and KnowledgeFlow reads both.

The samples are a good test because a real question crosses them. An engineer who creates a TPU VM without an external IP address, and then needs the internet, finds half the answer in the TPU docs and half in the Cloud NAT docs (§2.1). The published pages give the reference answer for each step.

§2 Problem Statement

Writers link topics well inside a documentation set. A link across sets needs a writer who knows the other product. Site search covers one set at a time, and it returns pages, not the path between them. Employees fill the gap by asking colleagues, and 53% of professional developers say that waiting for answers disrupts their workflow2.

Problem statement
Google's data center documentation is written as separate documentation sets, one for each product. Each set links well inside itself, but questions that cross sets have no path, so employees search each set in turn or ask an expert. A knowledge graph built by a language model can join the sets, but every edge it makes is a guess. Most of the edges already exist in the maps, relationship tables, keys and classifications that writers maintain, and no tool reads them.

§4 User Stories

Each story comes from the Goal and Success fields in §3. The acceptance criteria are what the checks in §5 test.

US-01 · Docs Platform Lead
As the Docs Platform Lead, I want every answer to show its path or say what it could not find, so that employees can trust answers across documentation sets.
Accepted when: every answer step cites a topic and an edge · a step that fails the checks is never delivered · every dropped step opens or updates a gap issue.
US-02 · Information Architect
As the information architect, I want links that the model finds to reach me as proposals, so that the content model stays under writer control.
Accepted when: model-found edges are stored as proposed · an answer that uses one labels that step · an approved edge becomes a relationship table row or link in a pull request · the next build reads it as authored.
US-03 · Senior Technical Writer
As a senior technical writer, I want each gap issue to show the question, the path found and the missing edge, so that I fix the links that cost readers the most time.
Accepted when: each gap issue has the question, the topics reached, the failed step and a suggested relationship table row · repeat questions add to one issue for each missing edge.
US-04 · Software Engineer
As a software engineer, I want a short answer with each step linked to its page, so that I get an answer about another team's product without waiting.
Accepted when: the answer arrives in under 20 seconds on the sample sets · each step links to its published topic.
US-05 · Technical Support Engineer
As a support engineer, I want values in answers to come from their key, for the right TPU generation, so that I never give a customer a value from the wrong page.
Accepted when: every keyed value in an answer matches its key value · an answer never mixes values from two generations unless the question names both.
US-06 · Lena (reader)
As an ML engineer, I want one answer that joins the TPU networking page to the Cloud NAT overview, so that my TPU VMs reach the internet without external IP addresses.
Accepted when: the answer cites topics from both sets · every edge between them is authored or labelled.
US-07 · Daniel (reader)
As a site reliability engineer, I want the timeout default and the rule behind it, so that I check the right value on my gateway.
Accepted when: the default and its rule come from the Tune NAT configuration topic · the command and field name match the source exactly.

§5 Proposed Design

KnowledgeFlow does one thing. It answers an employee's question with a path through the documentation, and it checks every step of the path. It is an agent built with Agent Development Kit (ADK), Google's open-source agent framework. ADK is licensed under Apache 2.0 and its agents can run on Cloud Run19. Gemini 3.8 Flash (gemini-3.8-flash, a stable model20) runs the agent and calls its tools through Gemini function calling21. The embedding model gemini-embedding-001 finds entry topics by meaning22.

The agent has six plain Python tools that give the same result every time, and two model steps. Gemini proposes edges from prose, and it writes the answer. The checks decide whether each step is grounded. The agent cannot change a check result, and it cannot add an edge to the graph as authored.

5.1 How it works

KnowledgeFlow has two parts. The build runs on every docs merge. It reads the structure of each documentation set and writes the graph. The answer runs on every question. It finds entry topics, walks the graph and writes a checked answer. Figure 4 adds KnowledgeFlow to the system in Figure 1.

Figure 4
System context: KnowledgeFlow added
Compare with Figure 1. The documentation sets and their teams stay as they are. The join that a reader or an expert made by hand now comes from edges that writers already maintain.
5.2 The graph

The graph has four node types and seven edge types. Six edge types come from structure. KnowledgeFlow reads them with lxml from DITA maps and topics, and with MyST-Parser from MyST pages, where MANIFEST kept reuse as includes, substitutions and targets3. One edge type comes from the model.

Figure 5
Node types and edge types
Every authored edge stores the file and line it came from. A proposed edge stores the sentence that Gemini quoted.
EdgeRead fromMeaningStatus

relatedRelationship table row11A task is supported by these concept and reference topics.Authored

links-toCross-reference, or MyST linkThe topic sends the reader to another topic.Authored
aboutSubject reference in a topic or map13The topic is about this subject.Authored
mentionsGemini, from prose that has no linkThe topic names this subject but does not link to it.Proposed

MANIFEST has no mapping for relationship tables. KnowledgeFlow reads them from the DITA source, which MANIFEST leaves unchanged3.

A shared subject scheme joins the sets. Each team classifies its own topics against the same subjects, once. Writers do not maintain a link from every TPU topic to every networking topic. The DITA standard expects this use: tools such as search tools can use subject classifications to find related content14.

One real thing is one node. Subject nodes take their names and aliases from the subject scheme, key names and topic titles. The TPU7x page is titled TPU7x (Ironwood), so both names resolve to one subject5. A name with no match in the subject scheme never becomes a new subject on its own. It becomes a proposal for the information architect.

5.3 Agent tools

1 · Build the graph build_graph

Runs in GitHub Actions on every merge to a documentation set. Parses DITA maps and topics with lxml, and MyST pages with MyST-Parser. Writes one document for each node and edge it reads, with the file and line it came from. Makes no model call.

Output: graph in Firestore · counts by edge type and by source

2 · Propose unlinked mentions (Gemini) propose_mentions

Gemini reads the prose of changed topics and lists subjects that a topic names but does not link. Each proposal must quote its sentence. A fixed check keeps a proposal only when the subject name or one of its aliases appears in that sentence. Proposals that pass are stored as mentions edges with the status proposed.

Output: proposed edges with the quoted sentence · changed topics only

3 · Find entry topics find_entry

Finds the topics where an answer starts. SQLite FTS5 ranks exact terms, such as flags, commands and version strings, with BM2525. Firestore vector search finds topics by meaning with a K-nearest-neighbour query23. Aliases resolve first, so Ironwood finds TPU7x topics.

Output: up to 5 entry topics, each with the match that found it

4 · Walk the graph walk_graph

Follows typed edges from the entry topics, up to three hops. It follows authored edges first, and proposed edges only when no authored path exists. It applies the audience and generation filter from the subject scheme, so a TPU7x question does not reach v5e values.

Output: candidate paths, each edge with its ID and status

5 · Compose the answer (Gemini) compose

Gemini writes the answer as numbered steps. Each step cites one topic and the edge that reached it, from the candidate paths only. Gemini may restate text from that topic. It may not add facts from outside the paths. On a failed check, it revises only the failed steps.

Output: answer steps with citations · at most 2 revisions

6 · Check the answer check_answer

Runs four checks. Source: every step cites a topic in the candidate paths. Literals: every number, unit, flag, field and command in a step appears in its topic or in its key value. Path: each cited topic is joined to the question's entry topics by edges in the graph. Labels: every step reached through a proposed edge carries a label.

Output: pass or fail for each step, with the reason

7 · Report the gap report_gap

Runs when a step still fails after two revisions. The agent drops the step and tells the employee what it could not answer. This tool opens one docs issue for each missing edge, with the question, the topics reached, the failed step and a suggested relationship table row. A repeat question adds to the same issue. Every question writes one row to the question log.

Output: gap issue · question log row

8 · Turn approved edges into structure record_review

For each proposed edge that an answer used, opens a pull request that adds the edge as a relationship table row in the DITA map, or as a link in the MyST page. Branch protection requires the information architect's approval33. After merge, the next build reads the edge as authored. A closed pull request is stored as rejected, so Gemini does not propose that edge again.

Output: edge pull request · rejected-proposal list
5.4 Agent loop

The agent runs find_entry and walk_graph, then asks Gemini to compose. check_answer tests every step. When a step fails, Gemini reads the reason and revises only that step, and the checks run again. After two failed revisions, the agent drops the step, says so in the answer, and report_gap opens an issue. No step reaches the employee without a passing check.

The build follows the same rule. Gemini proposes, a check filters, and a person approves. As approved edges become structure, fewer edges are proposed, so the model is called less at build time.

What happens to one question
Every path ends in an answer that contains only checked steps. A step that cannot be checked becomes a gap issue, not a guess.

5.6 Why build the graph from structure first

Microsoft's guidance is that GraphRAG suits a use case only when its benefits outweigh the upfront cost of building the graph index15. For DITA content, most of that index already exists.

ApproachHow edges are madeModel use at build timeWhat an edge is worth
GraphRAGA language model extracts a graph from every document15.Every documentInferred
LazyGraphRAGNo prior summarisation of the source data. A relevance test budget sets the cost and quality at query time16.Low at build time; model calls move to query timeInferred
KnowledgeFlowRead from maps, relationship tables, keys, conrefs, links and subject references. Gemini proposes only unlinked mentions.Prose of changed topics only; falls as proposals are approvedAuthored edges trace to a line

The build logs the number of edges from each source and the model tokens it used. So the share of edges that cost no model call is measured on every build, not estimated (§7).

§7 Success Metrics

The MVP runs on the three sample sets and an evaluation set of 30 questions. Each question has a reference path, written from the published pages, and half the questions cross documentation sets. The MVP succeeds if the numbers below are met. The first metric matters most: an answer with one unchecked step is worse than an answer that says what it could not find.
